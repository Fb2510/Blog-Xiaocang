Clash 节点测速超时却能上网？测速地址与健康检查排查

小仓2026-10-03— 次阅读
网络教程

**Clash 节点测速显示超时，并不一定意味着节点完全不可用。**先确认网页和测速使用的是同一个节点，再核对测速 URL、超时阈值与健康检查配置。网页能打开，也只能证明这次访问成功，不能据此认定所有网站都能正常访问。

本文适用于使用 mihomo 内核的客户端；不同客户端的按钮名称和测速实现可能不同。资料核对日期：2026 年 10 月 3 日。

测速、ping 和下载速度各说明什么？

Windows 的 ping 发送 ICMP 回显请求，用来观察对应 IP 路径的响应；客户端的 URL 测试则面向指定地址。两者的目标、协议和经过的路径可能不同，不能用一次 ping 结果替代代理访问验证。Microsoft ping 文档

mihomo 的 url-test 配置包含测试 URL；unified-delay 又会影响延迟计算方式。因此，比较两个节点前，应保持测速设置一致。短请求的延迟也不是长时间下载的吞吐量，视频卡顿应另看延迟、抖动与丢包排查。自动选择配置、统一延迟说明

按顺序检查，避免同时改多个变量

第一步：确认“能上网”的确是被测节点

先暂停下载，把相关手动选择组固定到待查节点，再重新打开目标网页。在客户端连接页核对实际代理链：网页可能走直连、另一个策略组，或者自动组已经切换了节点。只看到网页加载成功，还不足以验证被测节点。

mihomo 的连接信息包含代理链和匹配规则，可用来核对实际路径。如果不清楚规则如何选择出口，先看规则、全局与 TUN 的区别。连接信息文档

第二步：记录生效的测速条件

找到当前测试使用的 URL、超时值、期望状态码，以及最近一次测试时间。手动测试按钮与后台定时检查可能使用不同参数，核对时要区分是哪一种结果。

在 mihomo 代理组配置中，url 指定健康检查地址，timeout 以毫秒计；设置 expected-status 后，响应码必须满足该条件才被认为可用。例如，期望 204 的检查收到 200，即使连接已建立，也可能不符合检查标准。interval 则以秒计，别把两个时间单位弄反。代理组通用字段

第三步：通过本地代理复查同一个地址

以下是 Windows PowerShell 对照命令。先确认客户端已开启 HTTP 或 mixed 监听，把示例端口 7890 换成实际端口；如果当前测试 URL 不同，也替换 $probeUrl。

$probeUrl = 'https://www.gstatic.com/generate_204'
curl.exe -q --silent --show-error --noproxy "localhost,127.0.0.1" --proxy "http://127.0.0.1:7890" --connect-timeout 8 --max-time 15 --output NUL --write-out "HTTP=%{http_code} Total=%{time_total}s\n" $probeUrl
$LASTEXITCODE

--proxy 指定本地代理；这里的 --noproxy 列表只排除本地主机，避免已有 NO_PROXY 把这个外部测试域名绕过。NUL 丢弃响应正文，Total 是整个请求的耗时，单位为秒。8 秒和 15 秒只是演示限制，并非节点合格标准。curl 选项说明

读取结果时同时看 HTTP 状态、错误文字和退出码。没有加入 --fail 时，退出码为 0 也不能保证 HTTP 状态符合预期。curl 对照请求与客户端探测的连接复用、请求细节及计时方式可能不同，因此耗时不必完全相等；还要在连接页确认它最终经过了待查节点。

第四步：换目标做对照，再判断故障范围

保持同一节点和网络，用原测试 URL 与一个自己确认可访问的 HTTPS 页面分别测试，间隔几秒各重复三次。第二个页面的正常状态码可能是 200，不能机械套用原地址的 204 条件。下表是排查方向，不是对某个机场的实测结论。

观察结果 下一步检查
原测试地址失败，另一地址成功 测试域名的解析、访问路径和状态码条件
两个地址都失败，网页却成功 网页是否缓存或走了其他出口，以及本地代理端口
curl 可完成，客户端一直报超时 两边的 URL、超时设置、实际节点和错误日志
同一条件下结果时好时坏 记录失败时段、错误类型，再比较网络与节点

如果只在某些域名上失败，可继续按DNS 与 Fake-IP 排查检查；不要一次改 DNS、节点、测速地址和超时值，否则难以判断哪个变量起了作用。

第五步：区分代理组与代理集合的健康检查

节点通过 proxy-providers 引入时，还要核对对应集合的 health-check。官方文档明确说明，代理组的 url 健康检查针对 proxies 字段中的代理，不负责检查经 use 引入的集合代理。因此，只改组内地址，不一定改到了集合的检查地址。代理组检查范围

集合具有自己的启用开关、测试 URL、间隔、超时与 lazy 设置；启用懒惰检查时，未使用的集合节点可能不执行后台测试。先区分“本次测试失败”和“没有新的测试结果”，再决定是否调整。修改前备份配置，订阅更新后重新核对生效值。代理集合健康检查

两个常见问题

把超时调大，就算修好了吗？

更长的等待时间有助于确认请求能否最终完成，却不能证明链路稳定。比较修改前后的完成率和实际网页体验；若错误属于状态码不符或证书问题，单纯增加等待时间未必有效。

能否改成 HTTP，或者关闭证书校验？

换协议会改变测试条件，不能把结果直接当成原 HTTPS 问题已解决。遇到证书报错，先记录错误并检查时间和信任链；不要靠关闭校验掩盖问题。
